# Claude completion notification mod

`tasty claude install` installs the existing status hooks, the `tasty-notify` Claude Code function-hooks mod and its companion `tasty-notify-gate` plugin. Re-run install after updating Tasty and start a new Claude process. The mod API was checked against the installed Claude Code 2.1.307 bundled declarations and validator, and the gate against 2.1.312; it is early access, not a guarantee for every older or future CLI. Unsupported CLIs can use the Monitor procedure in [external interaction](https://github.com/zilhak/tasty/blob/develop/docs/dev-guide/external-interaction.md#부모-claude-운영-규약--monitor-arm).

## Installation and ownership

The stable directories are `~/.claude/tasty-managed/notify-mod` and its sibling `~/.claude/tasty-managed/notify-gate`, next to the existing user settings file. The gate is a separate plugin because a plugin's own hooks do not see prompts its timers submit; nesting it inside the watched mod folder would mix the two plugins' reloads and generated declarations. Its source sits below the mod's source folder only because the engine test runner cannot import outside a plugin folder. It does not depend on a debug/release instance, plugin installation directory or Tasty data home. The executable embeds the manifest, function-hook modules and state contract; ordinary plugin build/bundle/signing procedures still apply. No additional runtime asset staging is required. The embedded mod source lives below its owning Rust source module, so the existing src/lang/assets version gate also detects a TypeScript-only change. The Claude mod manifest has its own version, independent of the Tasty plugin manifest.

Install merges both absolute paths into the user settings `env.CLAUDE_CODE_PLUGIN_DIRS` path list (`:` on Unix, `;` on Windows), preserving other values and hooks. An entry already present once keeps its position; a missing one is appended, so upgrading a mod-only install appends the gate. It rejects a malformed environment/path list, separator-containing managed path, a symlinked managed subtree/asset/settings file or an unowned existing target directory. The existing settings parent is canonicalized (including ordinary directory aliases); a missing parent is resolved from its nearest existing canonical ancestor. This trusted parent boundary gives alias and canonical spellings one managed install/uninstall identity. Links below that boundary remain refused. A private ownership marker distinguishes the managed directory. Reinstall compares bytes and rewrites only changed assets/settings; `installed` and `updated` still describe hook events, while `mod_updated` reports a changed mod or path entry. An inherited process-level `CLAUDE_CODE_PLUGIN_DIRS` can override settings; preserve the managed entry there or remove that override yourself. Session profiles and reboot commands do not strip this variable or replace user settings discovery.

Uninstall removes only the exact managed path-list entries, installed asset names and empty managed directories of both plugins. Other path-list entries, environment keys and hooks survive. Unknown files, including Claude-generated declaration files, are retained with the ownership marker; the directory can therefore remain after uninstall. Installation and removal are ordinary filesystem operations, not an atomic transaction with Claude's live reload. Do not run install/uninstall concurrently with another settings writer. No installer writes to a caller PTY or changes authentication.

## Session watcher

At `session.start`, the mod reads literal `TASTY_SURFACE_ID` and `TASTY_PARENT_HOME` environment keys. Without a numeric surface and an absolute parent home it does not arm. It reads only that namespace's `notify/<surface>.log` and `.log.meta`. A new process starts at the observed EOF, ignoring old notifications; an initially absent file starts at zero when created. Initialization is awaited before the first prompt, so a fast child started by that prompt cannot finish before the cursor is armed. An unreadable/oversized initial snapshot refuses activation rather than establishing a later EOF that silently skips new work.

The watcher uses one owned, non-overlapping 500 ms `$.clock.after` chain, with no platform shell/process dependency. It coalesces complete lines into one prompt per poll, normally up to16KiB, allowing one longer complete line within a1MiB snapshot bound. Larger logs refuse the read until the writer has reduced them; the writer's256KiB cleanup threshold is not a strict file maximum. A fully consumed snapshot retains at most1MiB in module memory. Polls still inspect retention metadata and file stat, but suppress the body read while size/mtime/baseline are unchanged. Pending incomplete lines and refused submits do not enter that cache. Observable same-size rewrites are read and compared with the cached bytes; changed content restarts at zero, while a timestamp-only touch does not replay it. A rewrite indistinguishable in stat and metadata remains outside this observation contract. Offsets count UTF-8 bytes; incomplete lines wait for a newline. A normal successful delivery advances only to the last delivered newline. A refused prompt or transient read keeps that position for retry. It never resubmits a user's original task or writes terminal input.

The namespace, absolute `retention_start + byte position` cursor, delivery sequence and pending delivery live in `$.state`, which survives module reload, not in the persistent cross-session store. Claude2.1.307 reruns `session.start` on reload and cancels the old environment's pending timers. Repeated session.start in the same loaded registration and namespace reuses its existing watcher, including an accepted submission still awaiting its checkpoint. A different namespace retires the previous timer/owner; retired callbacks remain fenced. This prevents the same-registration start race without advancing the cursor before acceptance. A fresh module VM has no access to that in-flight owner; the pending delivery and gate below cover it. The same process keeps watching across `/clear`, which emits an end but no new start. Final process/session end cancels the timer. A different parent home/surface gets a fresh EOF cursor rather than another namespace's history.

The reader compares metadata around its bounded snapshot and retries a changed retention baseline. It follows the completion-log resume rules for accounted truncation, an observed uncounted shrink, a decreasing host baseline and observed deletion/recreation. It reads from the beginning after those resets. This API offers no shared filesystem lock, inode or host-generation identity: deletion/recreation entirely between polls, uncounted truncate/regrowth past the cursor and writer metadata failures have the existing completion-log uncertainty. Lost retained bytes cannot be reconstructed. Prompt acceptance and cursor commit are two API calls, and a queued plugin prompt outlives the module copy that submitted it; see the delivery gate below.

## Delivery gate

Before submitting, the watcher stores a pending delivery in its session state: a sequence number above its own last sequence and every sequence in the gate's record, the exact prompt text and the cursor it reaches. The text starts with a `[[tasty-notify N]]` line. The cursor passes the delivery only after the gate has confirmed that sequence entered. A module copy that finds a pending delivery resubmits that exact text, never a wider range; lines appended meanwhile follow as the next sequence. A pending delivery also survives a namespace change.

The gate hooks `prompt.submit` for prompts whose origin is the `tasty-notify` plugin and whose first line is that marker. In Claude Code 2.1.312 a plugin's queued prompt runs this chain when it enters, after a running turn ends. The gate's record has two parts. Before passing the prompt on (with the marker line removed), the gate claims the sequence as in flight with a versioned `$.state` write that names its own module copy. Only after the hooks beneath have let the prompt enter does it move the sequence to `delivered`. If the prompt is refused or the hooks beneath fail, it releases the claim. The watcher treats only `delivered` as confirmation, so a reloaded watcher polling while an entry is still running beneath the gate keeps its pending delivery. A sequence at or below `delivered`, or one still in flight in the same gate copy, is dropped with a short localized notice. A lost version race is also dropped. Every drop keeps the delivery pending, and the watcher resubmits it on a later poll. Therefore a queued copy from a replaced module and the fresh module's resubmission enter once between them, in either order, and no drop or refusal discards a delivery that has not entered.

Remaining limits: confirmation and entry are not one transaction. An in-flight claim left by a gate copy that was lost mid-entry (a worker loss or gate reload) is taken over by the next copy and the delivery is submitted again. Such a delivery may already have entered, so it can repeat, but it is not lost. If the gate is lost after the prompt entered but before `delivered` is written, the same repeat follows. The order and serial entry of queued plugin prompts are observed behaviour, not a documented contract. Without the gate (not installed, or a session that started before the install added its path), deliveries still arrive once per poll with the marker line visible, and a reload while a delivery is queued can deliver it twice; the guarantee starts with Claude processes started after install. A process crash or a new session starts from the new process's EOF as above. Session-state size limits for a pending delivery holding one long line (up to the 1 MiB read bound) are not documented or measured; a refused write keeps retrying.

## Activation marker

`TASTY_CLAUDE_NOTIFY_MOD=<surface-id>` marks a successfully initialized watcher in that Claude process and subsequent Bash children. Match the value to the actual surface before omitting Monitor; an inherited marker alone is insufficient. Outside Tasty, startup clears an inherited marker. Do not also arm Monitor when the mod is receiving: both consumers submit notifications. The marker is not a child result or an acknowledgement that the model completed a turn.

The mod calls `$.prompt.submit` without `asUser`: Claude supplies the plugin origin, and queues a separate turn when the current turn is idle. The visible heading explicitly says that status changes are not task-success evidence. Since this text is also user-visible, the mod ships English, Korean, Japanese and Simplified Chinese headings selected by `TASTY_LOCALE`; its sandbox cannot call Tasty's Rust translator. The existing log lines keep the writer's locale. The API's scheduling/origin contract and local engine tests are separate from a real authenticated model turn and the actual UserPromptSubmit status-hook observation.

## Verification boundary

Local `claude plugin validate` of both plugins, TypeScript checking, Claude's engine-based `plugin test` (with the gate loaded as an inline plugin), and Rust install/uninstall tests cover the module source, reader, gate and settings/assets invariants. The test runner runs hooks when the call is made, not when a queued prompt enters, and approximates a module reload by ending and restarting the session; it cannot reproduce the live reload order. The test runner supplies filesystem/clock/environment and submit stand-ins; it does not establish idle/busy real-model scheduling, hot-reload teardown in a live terminal, actual child completion delivery or UserPromptSubmit status updates. A real authenticated session must establish those acceptance observations before the full notification task is closed. Quota/authentication refusal is not a successful model response; do not change account, key, model or provider to bypass it.

For externally maintained instructions or conductor skills, skip Monitor only when this process's matching marker is present. Keep Monitor and periodic child reconciliation as fallback for unsupported/unloaded mods. Those user-owned files are not modified by the installer.
